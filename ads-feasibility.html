結論（3行）

①

条件付きでできる日影は自作できる。ただし段階を切る

計算そのものは軽い（実測：等時間日影図の生成 0.61秒）。規制値データも東京なら機械可読で取れることを実データで確認した。難所は逆方向の焼き直しで、そこは全自動を諦めて「探索の自動化」に置き換える。推奨＝L0 計算コア → L1 判定 → L2 日影図出力。ただし初期版は「確認申請の判定」ではなく「企画段階の設計支援・事前検証」と位置づけるのが誠実。

②

できるが、やる価値が薄い天空率は後回しでいい

技術的には日影と同系統で、むしろ時間積分が無いぶん単純（実測：1点0.25秒。ただし現状の実装精度は申請グレードに届かず、要改良）。それ以前にこの案件が扱う5制度のうち4制度は、そもそも斜線制限（法56条）が適用除外になる。天空率は「斜線を緩和する手段」なので、斜線が効かない制度では出番が無い。①を終えてから判断すべき。

③

「シームレス」は不可能ブリッジは作れる。ただし人が1回触る

調べた全ベンダ（ADS／i-ARM／GLOOBE／DRA-CAD 他）の公開情報にAPI・コマンドライン・SDK が一つも無い。公開手段だけでの全自動連携は無理。現実解は「入力の下ごしらえ」を自動化するDXF／CSV書き出しで、人の作業を数十分→数分に落とすこと。無料のADS相当ソフトは実質存在しない（ADS-win 55万円＋年8.4万円）。

1. まず前提：その制度、そもそも日影・天空率が要るのか

「ADSボタン」を作る前に確認すべきことがあった。都市開発諸制度は、建築基準法の高さ制限を条文レベルで外す制度だということだ。制度ごとに何が外れるかが違い、それによって①②の価値が根本から変わる。条文原文で確認した結果が以下。

特定街区 日影 不要斜線 不要
法60条3項「特定街区内の建築物については、第五十二条から前条まで並びに第六十条の三第一項及び第二項の規定は、適用しない」
＝法52条〜59条の2 が丸ごと適用除外。法56条（斜線）も法56条の2（日影）も法的には不要。都市計画決定の協議で日影検討を求められることはあるが、それは法規制ではない。
都市再生特別地区 越境日影のみ斜線 不要
法60条の2第5項で法56条（斜線）は適用しない。同第6項「第五十六条の二第一項に規定する対象区域外にある建築物とみなして、同条の規定を適用する。この場合における同条第四項の規定の適用については、同項中『対象区域内の土地』とあるのは『対象区域（都市再生特別地区を除く。）内の土地』とする」
＝自分の区域に落ちる日影は無視、区域外の日影規制対象区域に落とす日影だけが規制される。いわゆる越境日影。大規模再開発の日影検討の実像はまさにこれ。
高度利用地区 日影 必要隣地・北側斜線 必要
法59条4項：特定行政庁が許可した建築物は「第五十六条第一項第一号及び第二項から第四項までの規定は、適用しない」
＝除外されるのは道路斜線だけ。隣地斜線・北側斜線・日影規制は生きている。5制度のうち天空率に出番があるのは実質ここだけ（隣地・北側について）。
再開発等促進区 日影 必要斜線 不要
法68条の3第4項：許可した建築物については「第五十六条の規定は、適用しない」
＝斜線は全部外れるが、法56条の2（日影）は列挙されていない＝日影規制は生きる。
総合設計 日影 必要斜線 緩和可
法59条の2第1項：許可の範囲内で「第五十二条第一項から第九項まで、第五十五条第一項、第五十六条又は第五十七条の二第六項の規定による限度を超えるものとすることができる」
＝列挙に法56条の2（日影）が無い＝総合設計の許可では日影規制は緩和されない。日影は最後まで残る制約。

ここから導かれる優先順位

日影は5制度中4制度で生き残る（特定街区だけが完全に外れる）。一方、天空率が意味を持つのは高度利用地区の隣地・北側斜線だけ。つまり施主の直感どおり①が先、②は明確に後回しでいい。しかもこの「制度別の要否表」自体が、いま実装されていない価値ある情報だ。

出典：建築基準法（法令ID 325AC0000000201）第56条の2・第59条・第59条の2・第60条・第60条の2・第68条の3、施行令（325CO0000000338）第135条の5〜13。すべて e-Gov 法令API で条文XMLを取得し原文確認（2026-08-06）。

2. ① 日影：技術分解と実現性

2-1. 法が要求している計算要素

条文の構造を正確に押さえておく。重要なのは、冬至・真太陽時8〜16時・5m超という条件は「別表第4」ではなく法56条の2第1項の本文そのものに書かれていること。別表第4は地域・対象建築物・測定面高さ・時間数だけを定める。

時刻と日付 — 法56条の2第1項本文
「冬至日の真太陽時による午前八時から午後四時まで（道の区域内にあつては、午前九時から午後三時まで）の間において」
※真太陽時＝日時計の時刻。標準時ではないので均時差・経度差の補正が要る。北海道だけ時間帯が違う。
測定範囲 — 同 第1項本文＋別表第4（に）欄
「敷地境界線からの水平距離が五メートルを超える範囲において」＋（に）欄が「10m以内」「10m超」の2列。実質「5m超10m以内」と「10m超」の2本の規制線。
測定面 — 別表第4（は）欄
低層住専・田園住居＝1.5m／中高層住専・住居・近商・準工＝4m または 6.5m（条例で選択）。基準は「平均地盤面からの高さ」。
※非自明な発見：別表第4の「平均地盤面」の定義は単純な周囲接地平均で、通常の高さ算定に使う令2条2項の「地盤面」（高低差3m超なら3mごとに区分）とは別概念。実装時に混同すると数値がずれる。
みなし境界線の緩和 — 令135条の12第3項一号
敷地が道路・水面・線路敷等に接する場合、境界線は「その幅の二分の一だけ外側」にあるものとみなす。ただし幅が10mを超えるときは「反対側の境界線から敷地の側に水平距離五メートルの線」を境界線とみなす。
→ Phase3 は既に道路辺と幅員を持っているので、この緩和はそのまま実装できる。
高低差の緩和 — 令135条の12第3項二号
敷地の平均地盤面が隣地より1m以上低い場合、「当該高低差から1mを減じたものの二分の一だけ高い位置にある」とみなす。＝(H−1)/2。
複数棟の扱い — 法56条の2第2項
同一敷地内に2以上の建築物がある場合は1の建築物とみなす。＝基壇＋タワー＋別棟をまとめて1つの影として合成する。
越境日影 — 法56条の2第4項
「対象区域外にある高さ10mを超える建築物で、冬至日において、対象区域内の土地に日影を生じさせるものは、当該対象区域内にある建築物とみなして」規制する。
→ 商業地域の再開発が、隣の住居系地域に落とす影。この案件の主戦場はここ。

2-2. Phase3 のボリュームはそのまま使えるか → 使える

Phase3 のデータ構造を読んだ。結論から言うと日影計算にとって理想的な形をしている。

ボリュームの実体
Placement.podium / Placement.tower ＝ いずれも2次元の閉じた環（頂点列）。高さは metrics["h_podium"] / metrics["h_tower"] に別途スカラーで入る。つまり平面ポリゴンの鉛直押し出し（プリズム）。
座標系
envelope.Projection によるローカルENU（東西・南北・鉛直のメートル系）。Nが真北を向いている。日影計算は真北基準なので座標変換が不要。これは大きい。
テーパーのある形状
volume._volume_bands() が {h_low, h_high, ring} の階段状ソリッドを返す。斜線テーパー付きのボリュームも「高さ帯ごとのプリズムの積み重ね」で表現済み。
周辺データ
道路辺（幅員つき）・敷地環・用途地域・周辺建物（PLATEAU）が既に揃っている。みなし境界線の緩和も越境判定も、追加のデータ取得なしで組める。

これが効く理由：影が厳密に解ける

鉛直プリズムの影は、レイトレーシング（光線を飛ばして当たり判定する重い計算）を使わずに厳密解が求まる。ポリゴンPを太陽と反対方向へ、下端の高さぶんから上端の高さぶんまで平行移動させた「掃引」は、ポリゴンと線分のミンコフスキー和（2つの図形を足し合わせた図形）そのもので、Pの各辺が作る平行四辺形＋両端のPを合成するだけで正確に出る。近似ではない。

読み取れること

  • 計算速度は問題にならない。日影図2種の生成は1秒前後。Phase3が制度カード×方位で数十パターン回すことを考えても十分。
  • ただし計算領域が広い。150mのタワーは冬至8時に1km超の影を落とす。周辺建物や地形を含めた図を描くなら、現在のPhase3の描画範囲（数百m）を超える設計が要る。
  • 「厳密」なのは影の形であって、時間ではない。影のポリゴン自体は近似なしで解けるが、日影時間は1分ピッチで刻んだ離散和なので、規制値ギリギリの案では1分ぶんの誤差で判定が反転しうる。境界事例は「要精査」として人に返す設計が要る。

設計を1つ修正した（Codexレビューでの指摘）

当初は「5m線・10m線の線上だけ評価すれば合否が確定する」と考えていたが、これは誤り。条文が制限しているのは「5m超10m以内の範囲」「10m超の範囲」という面であって、線ではない。

影は建物から離れるほど短くなるとは限らない。基壇からセットバックしたタワーがある場合、10m線の点より遠い点の方が長く影に入ることが実際に起きる（近い点は低い基壇の影だけ、遠い点は高いタワーの影に入る）。凹形敷地や分棟でも同じことが起きる。線上だけ見ると判定が甘くなる。

したがって線上評価は「高速な一次スクリーニング」に格下げし、確定判定は面（区域全体）で等時間日影の超過領域を求め、それが規制線の内側に収まるかで行う。幸いラスタ積算が0.61秒なので、面でやってもコストはほとんど変わらない。

2-4. 規制値データは取れるのか → 東京は取れる（実データで確認した）

2-5. 段階案と概算工数

L0 — 計算コアと答え合わせ

概算 2〜3週間

単純敷地・平坦地・規制値を手入力、という限定条件で計算エンジンだけを作り、精度を固める。箱型・凹形・分棟・段状・浮いたボリューム・等時間線が分裂するケースをテストケースとして用意し、後述の案B（市販ソフトとの突き合わせ）で答え合わせする。ここを飛ばすと、後から数値がずれた時に原因が切り分けられない。

L1 — 判定（推奨：まずここまで）

概算 ＋3〜5週間

Phase3 の各制度カードについて「日影規制に抵触するか」を判定と実数で返す。区域全体を面で評価し、みなし境界線の緩和（令135条の12）、同一敷地複数棟の合成（法56条の2第2項）、越境判定（同第4項）、複数の規制値がまたがる場合まで含む。

  • 内訳：条文ロジック（緩和・越境・測定面・地域またぎ）8日／規制値データの取り込みと別表第一の対応表実装 4〜6日／面での判定と誤差管理 5日／テストと検証 4日
  • 判定は○×ではなく3値にする：適合（誤差を見ても規制値以下）／要精査（差が誤差の範囲内）／超過（誤差を見ても超過）。企画段階のツールとして、これが最も誠実で使える形。
  • 成果物：制度カードに「日影：適合／規制値4h に対し最大3.2h」のような1行が出る

L2 — 日影図2種を出力

概算 ＋1〜2週間

時刻日影図（8時〜16時の1時間ごとの影の輪郭を重ね描き）と等時間日影図（積算時間の等値線を2h/2.5h/3h/4h/5hで引く）。計算は L1 の副産物で、実測1秒未満。作業の実体は作図（Phase3ビューアへの重畳、方位記号、規制線、凡例、印刷体裁）。

L3 — ボリュームの自動焼き直し

概算 ＋3〜4週間・成功保証なし → 次章で正直に書く

施主の理想形「基準を守れるボリュームをフィードバック」。ここだけ難易度が段違いなので独立して評価する。

3. 逆方向（焼き直し）の難易度 — 正直に書く

「日影に引っかかったら自動で直す」は、順方向（判定）とはまったく別の問題だ。ここも憶測で書かず、実際に逆探索を回して確かめた。

3-1. 仮説：少数パラメータなので単調探索で解ける

Phase3 の massing は「基壇＋タワー」で、実質のパラメータはタワー高さ・プレート寸法・タワー位置・基壇高さ・広場位置くらいしかない。自由曲面の形状最適化ではなく、数変数の探索に落ちるはず——という見立てで検証した。

3-2. 実測結果：仮説は半分外れた

■ L3-a: タワー高さの二分探索（形状固定・北側隣接地に対象区域があると想定） 限度 5m線 4.0h / 10m線 2.5h 初期 H=200m -> 8.03h / 8.03h NG iter1 H=115.5m -> 8.03h / 8.03h NG iter5 H= 36.3m -> 8.03h / 8.03h NG iter9 H= 31.3m -> 8.03h / 8.03h NG => 適合最大高さ ≒ 31.0 m ＝ 基壇高さに張り付いて、なお NG （評価10回 / 12.0 s、1評価1.2s） ■ 犯人を特定：基壇（タワーを消して基壇だけで評価） 基壇 100x80m H=31m 単独 -> 8.03h / 8.03h NG 基壇 100x80m H=20m 単独 -> 8.03h / 8.03h NG 基壇 100x80m H=12m 単独 -> 8.03h / 4.27h NG 基壇 100x80m H= 8m 単独 -> 1.73h / 0.37h OK ■ 基壇を北側から後退させる（H=31m 固定） 後退 0m -> 8.03h / 8.03h NG 後退 20m -> 8.03h / 8.03h NG 後退 30m -> 7.60h / 6.97h NG 後退 40m（敷地の半分を空ける）-> 3.23h / 2.90h なお NG

この実測が意味すること

日影を拘束しているのはタワーではなく基壇だった。タワーをいくら削っても解けない。100m×80mの低層部が31m立っていれば、北側の規制線は一日中影に入る。基壇を8mまで下げるか、敷地の半分近くを空けるかしないと適合しない。

つまり L3 は「タワー高さを1変数で下げる」では絶対に解けない。基壇高さ・基壇外形・広場位置の連立になり、しかも容積は所与なので、日影で削った床はどこかに戻さねばならない。それは Phase2.5（広場配置）→ Phase3（配棟）のループに戻ることを意味し、収束の保証が無い。

3-3. だから L3 はこう置き換える

「全自動で正解ボリュームを吐く」のではなく、探索を自動化して候補を並べる形にするのが現実解。しかもこの案件は既に探索空間を持っている——制度カード × 広場位置（N/S/E/W/auto）× 空地率モードのグリッドがそれだ。

  1. 判定（L1）：現在の案が何時間オーバーしているかを出す
  2. 感度表示：基壇高さ／基壇北側後退／タワー位置を1つずつ振って、どの変数が何時間効くかを出す（実測1.2秒/評価なので、20点振っても25秒）
  3. 候補生成：規制線上の各点・各時刻について「その時刻に影を落とさない高さの上限」は z₀ + d·tan(太陽高度) で直接逆算できる。これを重ねると逆日影の包絡面（ADSの逆日影に相当する考え方）が作れる。ただし日影規制は「全時刻で影を落とすな」ではなく「合計◯時間まで」なので、どの時刻の影を許すかという組合せの選択が入り、包絡面だけでは解が決まらない。だから包絡面で候補を作り、順方向の計算で検証するという往復にする。
  4. 候補提示：既存の広場位置グリッドを日影で再評価し、「適合する配置はこれとこれ」と並べる

おまけの発見：既存パラメータと正面衝突する

build_phase25.py に PLAZA_NORTH_PENALTY = 0.15（北側広場は日照面で不利なので減点）というパラメータがあり、コメントに「日影の観点で高層棟を南に寄せる話は別途『日影軸』で評価する予定」と施主自身の言葉で書かれている。

今回の実測はまさにその答えになっている。北側広場は「広場自体の日当たり」では不利だが、「北隣に落とす日影」では決定的に有利。日影を入れると、この0.15という減点係数は再検討対象になる。予定されていた「日影軸」を、定性評価ではなく実数で埋められる。

4. ② 天空率：①とどこが同じで、どこが別物か

4-1. 制度構造（条文で確認）

定義 — 令135条の5
「天空率とは、次の式によつて計算した数値をいう。Rs＝（As−Ab）／As」As＝想定半球の水平投影面積、Ab＝建築物等を同一の想定半球に投影した投影面の水平投影面積。
判定の型 — 令135条の6〜8
計画建築物の天空率が、「斜線制限ぴったりに建てた仮想建築物（適合建築物）」の天空率以上であること。道路については加えて後退距離の比較も要る（令135条の6第2号）。
基準線 — 法56条7項（政令ではなく法本文に数値がある）
道路＝前面道路の反対側の境界線上／隣地＝隣地境界線から16m（勾配1.25の場合）または12.4m（2.5の場合）外側／北側＝真北方向に4m（低層住専・田園）または8m（中高層住専）外側。
算定位置の間隔 — 令135条の9・10・11
道路＝幅員の1/2以内／隣地＝8m（1.25）・6.2m（2.5）以内／北側＝1m（低層住専）・2m（中高層住専）以内。いずれも両端＋その間に均等配置。道路は「前面道路の路面の中心の高さ」を想定半球の中心とする。

4-2. ①との共通点・相違点

共通（＝①をやれば②が安くなる部分）

  • 同じ鉛直押し出しプリズムを入力に取る。ボリューム側の準備は完全に共用できる
  • 敷地環・道路辺・幅員・真北という同じ前提データを使う
  • 「指定された測定点の集合で個別に評価して、全点で合否を取る」という評価の型が同じ
  • 高低差1m以上の緩和が (H−1)/2 という日影と同じ式（令135条の9第4項）

別物（＝②固有の追加コスト）

  • 時間の代わりに立体角。日影は「2D平面上の影を時間積分」、天空率は「3Dの見え方を半球に投影して面積比」。ただし鉛直プリズムなら方位θごとに遮蔽される仰角区間を求める1次元積分に落ちる（後述の実測どおり厳密解に収束する）。
  • 「適合建築物」という仮想立体を作る必要がある。ここは朗報で、envelope.build_birdcage() / shahen_reference() / hlimit_reference() が既に斜線包絡面を生成している。素材は揃っている。
  • 制度の場合分けが泥沼。2以上の道路がある場合の区域分割、屈曲道路、敷地が複数地域にまたがる場合——実装コストの大半はここで、幾何計算ではない。
  • 精度要求が日影より厳しい。合否が0.01ポイント差で決まるため、近似（魚眼画像のピクセル数え等）では確認申請グレードにならない。

4-3. 実測：天空率もプロトタイプを書いた

正射影（半球を真上から見た投影）では、仰角eの方向は半径 cos(e) に写る。よって遮蔽面積は方位θについての1次元積分に落ちる。実際に計算した（敷地60×40m、南に幅員20m道路、勾配1.5・適用距離30m相当の適合建築物と比較）。

■ 道路の算定位置（反対側境界線上・5m間隔）での比較 x= 0.0 計画 86.178% / 適合 88.368% 差 −2.190pt NG x=15.0 計画 80.645% / 適合 81.608% 差 −0.962pt NG x=30.0 計画 78.349% / 適合 79.634% 差 −1.285pt NG x=60.0 計画 86.178% / 適合 88.368% 差 −2.190pt NG （13点 × 2建物 = 56.1 s。1点あたり約0.25秒/建物） ■ 方位分割数と収束（x=30.0 の計画建築物） n= 90 -> 78.869892 % 0.01 s n= 360 -> 78.195212 % 0.07 s n= 720 -> 78.289603 % 0.13 s n=1440 -> 78.349467 % 0.25 s n=2880 -> 78.295991 % 0.47 s

※このモデルは「150mのタワーが道路斜線の適合建築物より天空を塞ぐ」という当たり前の結果を返しているだけで、実物件の判定ではない。確認したかったのは計算が成立し、実用速度で解が求まることで、それは確認できた。

ただし精度は足りていない（正直に）

上の収束表をよく見ると、分割数を倍にしても値が78.19 → 78.29 → 78.35 → 78.30 と単調にならず0.05ポイント幅で振動している。方位を等間隔で刻むと、建物の角がちょうど分割線に乗ったり外れたりするために起きる正常な挙動だが、天空率の合否は0.01ポイント差で決まるので、この精度では申請グレードを名乗れない。

対策は分かっている：等間隔をやめ、建物の全頂点の方位角を積分の分割点に入れて、遮蔽の切り替わり区間ごとに適応的に積分する。加えて、令135条の5 の定義が Ab を「建築物及びその敷地の地盤を投影した投影面」としている以上、算定位置が敷地地盤面より低い場合は地盤自体も遮蔽物に含める必要がある。②に着手する時は、この2点が最初の実装課題になる。

②の結論

技術的にはできる。時間積分が無いぶん、コアの数式は日影よりむしろ単純だった。だが1章の制度整理どおり、5制度中4制度で斜線そのものが適用除外になる。天空率は斜線を緩和する道具なので、外れている制度では使い道がない。投資対効果で①に大差で負ける。①を出し切ってから、高度利用地区の隣地・北側斜線に需要があるかを見て判断すべき。

5-2. 「本当に無料のADS」は存在するか → 実質しない

  • 確認申請グレードの完全無料ツールは見つからなかった。探した範囲：フリーソフト（窓の杜・Vector・個人開発）、Webサービス、自治体提供、SketchUpプラグイン。
  • 見つかった無料系は消費者向けの簡易日照シミュレーションのみ（「日当り君」＝2017年以降更新なし・天空率なし、PLATEAU利用の地図系Webサービス＝規制判定用ではない）。
  • SketchUpプラグイン「1001日影＆天空率」はデモ版無料だが、サイト記載が2009年で止まっている。
  • ADS の体験版は14日間。ADS-BT for Vectorworks の公式明記では「体験版は各種表の出力は出来ません」。ただし期限後も「ADS-win／LAとのデータコンバータ」としては使い続けられると公式に書かれている——ここは③の設計で使える可能性がある。

5-3. 自動連携の口はあるか → 無い

これが③の結論を決めた

調べた全ベンダ（ADS／i-ARM／B-MOS／DRA-CAD）の公式サイトに、API・コマンドライン・SDK・スクリプト機能の記載が一つも無かった。公開情報として案内されている連携手段はすべてGUIのインポート／変換ツール。したがって「ボタンを押したら市販ADSが裏で回って結果が返ってくる」は公開されている手段の範囲では実現できない。

※非公開の連携手段や、法人向けの個別対応まで否定するものではない。本気で連携するならベンダに直接問い合わせる価値はある（特に i-ARM の構造システムは入力形式の開放度が高く、話が通る可能性がある）。

さらに ADS の実運用フローを公式FAQで確認したところ、DXFを取り込んだ後は「与条件設定→本敷地」で人間が図形をなぞって（トレースして）敷地・建物を確定させるのが基本だった。図形をそのまま敷地として自動認識するわけではない（自動トレース機能「外部図形変換」も別途あるが、レイヤ命名規約が公開されていないため精度は実機検証が必要）。

5-4. だから、現実的なブリッジはこう作る

案A（推奨）— 「入力の下ごしらえ」を出力する

概算 1週間 ＋ 実機検証

Phase3 から、ADS／i-ARM が食える形で敷地・道路・建物ボリューム・方位・与条件を書き出す。人の作業を「ゼロから入力」から「読み込んで確認」に変える。シームレスではないが、実務の手間はここで9割落ちる。

  • DXF（3D）：敷地境界／道路境界＋幅員／基壇・タワーのプリズム をレイヤ分けして出力。Phase3 は既に ENU メートル座標を持っているので変換は素直。
  • CSV / JSON：i-ARM が CSV・JSON・GML(PLATEAU) を直接食えるので、ADSよりこちらの方が自動化の余地が大きい。連携先として第一候補。
  • 与条件（用途地域・建蔽率・容積率・日影規制の号・測定面）も併せて書き出す。ツールは既に全部持っている。

案B — 逆向きに使う：ADSを「答え合わせ」に使う

概算 数日（自作L1の検証工程として）

国交省がPLATEAU実証でやったのと同じ手（レポートp.27で「専用ソフトウェア『ADS』により例示」と明記）。自作L1の判定結果を、代表案件でADSの結果と突き合わせて精度を担保する。①の信頼性を最も安く買える方法で、ADS-LA（15万円）または体験版14日で足りる可能性がある。

案C — GUI自動操作（RPA）

非推奨

APIが無いのでGUIを自動操作する発想はあり得るが、ベンダのバージョンアップで即壊れる・利用規約の確認が要る・確認申請の成果物に使う品質を担保できない。伝聞にある「ADSのバイナリをAIで使えるようにした」件も、裏取りできていないので技術的可能性の信号としてのみ扱い、設計の前提には置かない。

7. 残る不確実性（確認できていないこと）

  • 東京都の日影規制レイヤが「別表第一（原則パターン）」をどこまで含むか。属性の作りからは例外・追加指定（別表第二〜五）が主と読めるが、原則区域が全部含まれるかは未検証。含まれない前提で対応表を実装する想定にしてある。
  • 東京都以外の自治体は未調査。同じ形でデータが出ているとは限らない。ツールの当面の対象が都内なら問題にならない。
  • ADS のDXFレイヤ命名規約・独自ファイル拡張子は非公開。案Aの「どこまで自動認識されるか」は実機で1回試すまで確定しない。
  • 日影計算の時間ピッチの実務標準（何分刻みが確認機関に通るか）を定める公表統一基準は特定できなかった。日本建築行政会議のサイトにも該当なし。ベンダの製品仕様に「60分または30分刻み」の記述は見たが業界標準ではない。自作する場合は安全側（細かいピッチ）で組み、案Bの答え合わせで担保する。
  • ADSの逆日影・逆天空率の機能仕様は一次情報で取れていない。メーカー公式サイトが外部アクセスを拒否（403）するため、検索結果の要約でしか確認できていない。それによれば逆日影＝斜線と日影の両方に適合する建築可能範囲をメッシュ・等高線・断面で表示、逆天空率＝不適合な計画建物を「ナビゲーション」「オートカット」で解消する形状に修正、とされるが裏取り未了。
  • 天空率の告示：e-Gov法令データベースでは「天空率」を含む告示はヒットせず、算定式・算定位置・間隔はすべて政令本文に直接書かれていることを確認した。別途の告示委任は確認できていない。
  • 日建設計でADSのバイナリをAIで使えるようにした人がいる、という伝聞は裏取り不可能。本レポートでは事実として扱っていない。

日影・天空率とも計算機能の実装は可能で、企画段階の比較検討には十分に有効。一方、確認申請と同等の適合判定を名乗るには、区域全体の評価・数値誤差の管理・自治体ごとの法令と行政運用の確認が別途要る。初期版は「設計支援・事前検証」として出すのが正しい。
