0. 1画面サマリ（結論）

推奨＝Google Cloud の仮想サーバー（VM）1台に丸ごと引っ越す。東京・8vCPU。認証は今使っている Cloudflare のまま。

項目内容
構成GCE（Google Compute Engine＝Googleクラウドの仮想サーバー）e2-standard-8（8vCPU/32GB）東京 1台＋ディスク100GB。Cloudflare Tunnel＋Cloudflare Access（今と同じ仕組みをそのまま移設）。同時ジョブ3本。
月額約 4.8万円／月（税込・24時間稼働・認証は無料枠内・159.8円/USDで換算）
トライアル3ヶ月 総額約 14.3万円（税込）＋ 移植・検証作業 5〜7人日
安くする手夜間・週末を自動停止すると 約1.9万円／月（3ヶ月 約5.8万円）。国内VPSなら 約1.2万円／月（3ヶ月 約3.5万円）。

理由 3行

  1. 今のコードがほぼそのまま載る。 順番待ちキュー・認証（Cloudflare Access のトークン署名検証）・「自分のジョブしか見えない」所有者分離はすでに実装済み。作り直すのは Linux 用の起動設定・日本語フォント・Windows専用パス数箇所だけ。
  2. 重いのはCPUだけ。 1ジョブ＝実測 330〜380秒のCPU計算で、GPUもデータベースも要らない。しかも1ジョブがほぼ1コアしか使わないので、「コア数＝同時に流せる本数」という単純な設計で足りる。分散させるほうが壊れやすい（§3-B）。
  3. 調達ゼロで即日始められて、終われば消すだけで課金が止まる。 SD既存のGoogle Cloud に1台足すだけ。VPSは月額固定・最低利用期間つきで、新規契約の手続きぶんトライアル開始が遅れる。

先に決めてほしいこと（詳細は §8）

  • 「10アカウント」と「100人」の関係。10個のIDを100人で使い回すなら「誰がやったか」の記録が取れなくなる（監査上まずい）。100人全員を識別するなら100個のメールアドレス登録が必要で、Cloudflare の無料枠50人を超える（超過分 $7/人/月）。
  • サービス水準。本提案は1台構成＝単一障害点（SPOF＝そこが壊れると全部止まる箇所）あり。「冗長化された高可用システム」ではない。復旧目標（RTO）・データ復旧点（RPO）を先方と合意する必要がある。

1-3. すでに出来ていること（＝作り直さなくていい）

2. どれだけの機械が要るか（サイジングの根拠）

2-1. 需要の見積り

「10アカウント・100人まで」の内訳を、重さで2つに分ける。

種類中身重さ同時100人でどうなるか
閲覧・地図操作HTML/JS/下図タイルの配信。タイルは生成済みならファイルを読んで返すだけ（0.1秒）軽い。1人あたり初回6MB＋タイル10〜30枚1台で余裕。ディスク読み出しと帯域の勝負で、CPUはほぼ使わない
STARTジョブphase25→phase3→phase35 のCPU計算重い。1本 330〜380秒・ほぼ1コア占有ここだけがボトルネック。同時に流せる本数＝実質コア数

現実的な使われ方＝10アカウントが各自2〜5回/日回す＝1日20〜50ジョブ。
最悪ケース＝説明会で10人が一斉にSTARTを押す。

2-2. 同時ジョブ数と待ち時間（1ジョブ360秒＝6分として計算）

10人が一斉に押したとき、最後の人は (ceil(10/N)-1) × 6分 待ってから開始し、そこから6分で完成する。

同時本数 N必要vCPU（web・タイル・出力用に2つ残す）最後の人の開始まで最後の人の完成まで判定
1（今の既定）4 vCPU54分60分✕ 説明会で破綻する
38 vCPU18分24分○ 推奨（通常利用）
4（コード上限）10〜12 vCPU12分18分△ 費用対効果が薄い
6（コード改修要）16 vCPU6分12分説明会の日だけ一時的に上げる用
  • 同時3本＝.sim_env に SIM_MAX_CONCURRENT_JOBS=3 と書くだけ（コード変更ゼロ。上限4までは実装済み）。
  • 24分をJREが許容できるかは、サーバのスペックではなく先方と合意するサービス水準の問題。「各自が好きな時に回す」なら十分。「10人が画面を見ながら待つ説明会」には長い → その日だけ 16vCPU に変更（停止→マシンタイプ変更→起動で数分）して同時6本にする運用を推奨。
  • 注意：クラウドの「vCPU」は物理コアではなくハードウェアスレッド（1コアを2つに見せている単位）で、E2シリーズは割り当て時にIntel/AMDのどちらになるかが選べない。施主PCでの実測がそのままクラウドで再現する保証はない → §7-3 の技術検証（1〜2日）で同時1・3・4本を実測してから確定する。
  • メモリ：常駐0.18GB＋ジョブ1本あたり1〜1.5GB＋Chromium出力0.5〜1GB → 同時3本で8GB前後。16GBで足り、e2-custom-8-16384（8vCPU/16GB）にすれば月約7,000円安くなる見込み。ただし単価を公式ページで直接確認できていないため、本提案の金額は確実に裏の取れた e2-standard-8（32GB）で出している（§6-4）。
  • ディスク：コード＋data 264MB＋cache 479MB＋out 30MB/ジョブ。3ヶ月で500ジョブ回っても約15GB。100GBで十分（スナップショットはVMのディスク内には保存されないので、その分の余裕は不要）。

2-3. 可用性の考え方（正直に書く）

「冗長性がある」とは書かない。本提案は1台構成＝SPOF あり・ベストエフォート運用である。

トライアルに「サーバ2台構成」は勧めない。 理由＝今の作りは「順番待ちキューがプロセスのメモリ内」「結果 out/ がローカルディスク」「下図キャッシュがローカルディスク」で、状態が1台に貼り付いている。共有キューも排他制御も無いまま2台にすると、壊れ方のパターンが増えるだけで可用性は上がらない。

代わりに「1台をしぶとく生かす＋壊れたら確実に戻せる」で組む（＝パイロットライト方式）。

障害復旧手段目標時間利用者への影響
プロセスが落ちたsystemd Restart=always（自動再起動）10秒以内実行中ジョブは中断→「もう一度START」
OSがハングしたクラウド側の自動再起動数分同上
ディスク／VMが壊れたスナップショット＋構築スクリプトから別ゾーンへ復元RTO目標 30〜60分前回スナップショット時点まで戻る
Cloudflare Tunnelが切れたcloudflared も systemd 常駐＋自動再接続数十秒一時的に開けない
  • RTO（復旧目標時間）は「訓練で実測した値」しか約束しない。 トライアル開始前に一度、実際にスナップショットから別ゾーンへ復元してTunnelを繋ぎ直し、実測時間を記録する（§7-3）。
  • RPO（どこまで戻るか）＝日次スナップショットなら最大24時間。 ジョブ結果は再実行できるので実害は小さいが、明示しておく。
  • 稼働中のスナップショットは原則「クラッシュ整合」（電源をいきなり抜いた状態と同等）。本システムはデータベースを持たずファイルを書くだけなので実害は小さいが、取得は利用の少ない時間帯に回す。
  • 同時アクセスの捌き方：serve.py は ThreadingHTTPServer（リクエストごとにスレッド）でバックログも拡張済み。100人の閲覧なら問題ない。大人数の説明会をやる回だけ SIM_AUTOWARM=0（下図の裏側での作り置きを止める）にしてCPUを利用者に全部回す。

2-4. 順番待ちの永続化（Stage 1 に前倒し／L7）

現状はキューもジョブ状態もプロセスのメモリの中だけなので、再起動すると「待っていた人の順番」も「実行中のジョブ」も消える。トライアルでこれは説明しづらいので、最小限の SQLite（1ファイルで動く軽量データベース）台帳を入れる。

  • 保存するもの：job_id / 所有者（Accessのメール）/ 再実行に必要な入力の参照 / 状態（queued・running・succeeded・failed・interrupted）/ 投入・開始・終了時刻 / 試行回数 / 出力先。
  • 再起動時の扱い：queued はそのまま再投入、running は interrupted に落として画面に「中断されました。もう一度実行してください」と出す。途中から再開する機能は作らない（過剰）。
  • これはプロセス再起動には効くが、VM・ディスクごと壊れる障害には効かない（そこはスナップショットの担当）。
  • 副産物として監査ログ（誰がいつ何を回したか）が残る＝§4-4 の要求も同時に満たす。

案B（Stage 1 では非推奨）— コンテナ＋ワーカー分離（Cloud Run 等）

「Webはコンテナ、重い計算はジョブワーカー」という一般論としては正しい形で、本番（Stage 3）の行き先はこれ。だが今のコードのままでは Stage 1 に採れない。

  • 時間の問題ではない：Cloud Run のリクエスト上限は60分、Cloud Run Jobs は168時間なので、6分の処理は余裕で収まる。
  • 合わない本当の理由（3つとも作り替えが要る）
    1. 順番待ちキューとジョブ状態がプロセスのメモリ内。最小インスタンス1にしてもコンテナは任意に作り直されるので、そのたびにキューと実行中ジョブが消える。→ データベース化が必要（＝L7を大きく超える規模）。
    2. 結果 out/ と下図 cache/ がローカルディスク。Cloud Run のファイルシステムはメモリ上で停止時に消える＝毎回479MBのキャッシュが飛び、1枚37〜104秒の再生成地獄になる。Cloud Storage FUSE（オブジェクトストレージをフォルダのように見せる仕組み）は上書き・リネーム・ディレクトリ操作の挙動が普通のファイルシステムと違うので、そのままでは動かない。
    3. UIが1秒ごとに /job_status を叩くポーリング方式＝「同じインスタンスに繋がり続ける」前提。複数インスタンスになると状態が見えなくなる。
  • 結論：「Cloud Run でも工夫すれば動くが、VMより複雑で信頼性が下がる」＝Stage 1 では不採用。Stage 3（§7）で正解になる。

案C（コスト最優先）— 国内VPS 1台

  • 中身は案Aとまったく同じ（同じLinux・同じsystemd・同じCloudflare Tunnel/Access）。違うのは箱と課金だけ。
  • 月額が案Aの1/4程度。転送量無制限・固定料金で読みやすい。
  • 弱点：①スナップショット/復元やスペック変更がクラウドほど柔軟でない ②最低利用期間がある（さくらは3ヶ月）＝トライアル終了で即止められない ③新規契約の手続きが要る＝トライアル開始が遅れうる ④SDの既存クラウド管理（権限・監査・請求）の外に出る ⑤「8コア」の実性能はGCEと同じとは限らない（共有CPU・混雑時の性能低下）。§7-3 の技術検証を通してから選ぶこと。「機能面は何も落ちない」と無条件には言えない。
  • こういう時に選ぶ：トライアルが確実に3ヶ月以上続く／コスト最優先／SD側にVPS運用の担当がいる。

案D（参考）— 現状維持（施主PC＋Cloudflare Tunnel）

費用0円だがJREに出す構成としては不可。理由＝①PCの電源・スリープ・再起動でサービスが落ちる ②施主がPCを業務で使う＝重い作業とジョブが食い合う（空きメモリが657MBまで落ちてPlaywrightが落ちた実測記録あり）③GPUドライバ起因のブルースクリーン実績あり ④個人PCに顧客の検討データが載る。比較の基準線としてのみ記載。

4-3. 「10アカウント／100人」問題（要判断）

  • 10個のIDを100人で共有する：Cloudflare の費用は0円のままだが、「誰がそのジョブを回したか」が分からなくなり、SIM_PUBLIC_OUT=session の所有者分離も10グループ単位になる（同じIDの人同士は互いの結果が見える）。JRE内部の情報管理として許容されるか、先方に確認が要る。
  • 100人全員を個別に登録する：監査性は完璧だが、Cloudflare の無料枠50人を超える＝50人超過分に $7/人/月（100人なら $350/月 ≒ 5.6万円/月）。
  • 推奨の落としどころ：まず実際に使う人数を先方に確認する。50人以内なら全員個別登録が無料で最良。50人を超えるなら「部署単位で共有IDにするが、アプリ側の SQLite 台帳（L7）に投入者を必ず残し、共有IDの範囲内では互いの結果が見える」ことを明記して合意する。

5-3. タイルキャッシュ（479MB）の持ち込み ← 省略すると事故る

  • サーバ上では SIM_AUTOWARM=1（暇な時だけ自動補充）を維持。説明会の回だけ0にする（§2-3）。

7. 推奨案と、本リリースへの移行段階

7-1. 推奨＝案A改（GCE 8vCPU 東京 1台・24時間・Cloudflare Tunnel＋Access・同時3ジョブ・SQLite台帳つき）

決め手は3つ。①今のコードがそのまま載る＝移植5〜7人日で済み、トライアルの中身（諸制度の判定ロジック）に一切手を入れずに済む。②重いのはCPUだけなので、分散させるより1台を太らせるほうが安く・単純で・壊れにくい。③調達ゼロで即日始められて、終われば消すだけで課金が止まる。

コスト最優先の指示が出たら 案C-1（Xserver VPS 16GB・月11,770円）へ差し替えられる。構成もコードも運用手順も同一なので、§7-3 の技術検証を通してから最後に決めればよい。

7-2. 段階案（トライアル → 本リリース）

Stage 1（本提案・βトライアル3ヶ月）：VM1台・同時3ジョブ・Cloudflare Access。SQLite台帳で「待ち行列の復元」と「監査ログ」だけ確保。「実行中ジョブは再起動で中断」「計画停止中は使えない」「RTO 30〜60分／RPO 24時間」を先方に明示して合意する。
↓ ここで得たい実データ＝1日あたりの実ジョブ数・同時押しの実際の山・待ち時間の許容度。Stage 2 の設計はこの実測で決める（今は想像で作らない）。

Stage 2（本リリース初期・〜数十社）：ボトルネックが出た順に、①ジョブ台帳を本格的なデータベースへ ②out/ をオブジェクトストレージへ（保存期限管理とサーバ入れ替えが可能になる）③計算ワーカーを別VMへ分離（計算だけ増やせる）。①〜③が済んで初めてWeb側の複数台化に意味が出る。認証は Cloudflare Access のまま、顧客企業のIdP（SAML/OIDC＝会社のログイン基盤との連携）へ拡張。

Stage 3（本格運用・課金開始後）：Web＝Cloud Run、受付＝Cloud Tasks/Pub/Sub、計算＝Cloud Run Jobs（1タスク最大168時間なので余裕）、成果物＝Cloud Storage、下図キャッシュ＝共有ストレージ＋CDN。§3-B の案Bはここで正解になる。トライアルの段階で先取りしない（先取りすると壊れる箇所が増えるだけで、まだ得るものが無い）。

7-3. 着手順（優先順位つき）

  1. JREとサービス水準を合意する（先に決めないと機械が決まらない）。「最後の人が24分待ちで許容か」「10アカウントと100人の意味」「計画停止の枠」「RTO/RPO」「トライアル終了後のデータ削除」。

  2. 24時間稼働か、夜間週末停止か（停止なら月4.8万→1.9万。ただし「夜間・週末は開けません」と先方に言う必要がある）。
  3. 「10アカウント／100人」の実態（§4-3）。50人以内なら全員個別登録が無料で最良。
  4. 公開ドメインを sim.mud-ai.com（MUD-Ai名義）のままにするか、SD名義の新ドメインにするか。JRE向けの正式配布なら後者が自然。
  5. JRE側情シスへの事前確認を、いつ・誰から依頼するか。
  6. 移植・検証（5〜7人日）を誰がいつやるか。 L1（フォントによるレイアウト崩れ）と L2（Windowsパス由来の黙った機能欠落＝鉄道が3Dビューから消える等）は、実測で潰すまで「完了」と言えない。
